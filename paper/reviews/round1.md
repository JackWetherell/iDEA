# Referee report, round 1

**Manuscript:** "iDEA: an open-source Python framework for exact many-electron quantum mechanics and density functional theory in one dimension". Submitted to *Computer Physics Communications*, Computer Programs in Physics section.

**Code reviewed:** the repository at the commit that carries the draft (`iDEA/`, `tests/`, `benchmarking/`, `paper/scripts/make_figures.py`, README.md, CITATION.cff).

**Recommendation: major revision**

---

## Summary of the submission

The manuscript describes iDEA 1.1, a pip-installable Python package for one-dimensional model systems of a few electrons. The package provides:

- exact diagonalisation of the many-electron Hamiltonian on a real-space grid, using sparse Lanczos (ARPACK) on the full N_x^N spatial product space followed by explicit antisymmetrisation with a spin product function;
- exact time propagation, using the action of the matrix exponential;
- a common self-consistent-field (SCF) driver for non-interacting, Hartree, Hartree-Fock (HF), LDA, hybrid and KS-SCE methods, including their time-dependent versions;
- reverse engineering of exact Kohn-Sham (KS) and other fictitious-system potentials, for both the ground state and the time-dependent case;
- optional CuPy GPU acceleration of the exact solver.

The validation section compares the exact solver with a separated centre-of-mass/relative-coordinate reference for Hooke's atom (Table 1). Three examples follow: ground-state densities from each method (Fig. 1), exact KS and xc potentials (Fig. 2), and dipole dynamics after a field kick (Fig. 3). All numbers in the paper are generated by a single script, `make_figures.py`, and I could trace each macro in `numbers.tex` back to that script.

The code fills a real niche. It is used widely within the Godby group's research and in teaching. The paper is concise, and its fully scripted generation of every figure and number is commendable. I checked the technical claims against the source and ran parts of the code. Several advertised features are incorrect or do not work as described:

- restricted HF and restricted hybrid give energies far below the exact ground state;
- the KS-SCE method crashes on the paper's own test system and has an O(δx) total-energy error;
- the code listing in the paper does not terminate;
- the excited-state bookkeeping for three electrons is misaligned;
- the GPU time-propagation claim contradicts the repository's own benchmark documentation.

In addition:

- the quantitative tail comparison in Fig. 2 rests on a gauge choice that pins the potentials at the point where they are least well determined;
- the time-dependent validation does not actually test time stepping or many-body dynamics;
- the "restrictions" part of the program summary is missing.

All of these can be fixed, so I recommend major revision rather than rejection.

## MAJOR issues

### M1. Restricted HF (and restricted hybrid) is wrong for spin-unpolarised systems

`hartree_fock.hamiltonian` builds the spin-independent Hamiltonian with the exchange operator of the *total* density matrix:

```python
Vx = exchange_potential_operator(s, up_p + down_p)   # hartree_fock.py:67
H = K + Vext + Vh + Vx                               # hartree_fock.py:70
```

With `restricted=True`, this `H` is used for both spin channels (`non_interacting.py:306-308`, `334-336`). For a closed shell, exchange must involve only the same-spin density matrix, ρ_σ = ρ/2. The restricted calculation therefore doubles exchange. `hybrid.py:57,61` has the same bug.

I verified this numerically. For the softened He-like atom (`"ud"`, 101 points on [-10, 10]):

| Method | Energy (Ha) |
|---|---|
| Unrestricted HF | -1.7113 |
| **Restricted HF** | **-2.8757** |
| Exact | -1.7223 |
| Unrestricted hybrid | -1.7094 |
| **Restricted hybrid** | **-2.5902** |

Restricted HF thus lies 1.15 Ha *below* the exact energy, which is variationally impossible.

The existing test (`test_methods.py::test_hartree_fock_two_electron_singlet`) does not catch this. It only checks that E_x = -E_H/2, which holds for any doubly occupied orbital whether or not the SCF is correct.

The paper advertises "restricted and unrestricted Hartree–Fock (HF)" (Sec. 2). The authors should:

- fix the bug (use ρ/2, or ρ_σ, in the restricted Hamiltonian);
- add a test that restricted and unrestricted HF agree for a closed-shell two-electron singlet;
- state which variant was used for each figure.

### M2. The code listing does not run to completion, and the iterative solvers have no safeguards

I ran the listing in Sec. 2 verbatim. It never terminates:

1. The non-interacting step converges.
2. `hartree.solve` with the default `mixing=0.5` converges to ∫|Δn| ≈ 10⁻⁴.
3. It then locks into a two-cycle with ∫|Δn| = 0.53373 indefinitely. I stopped it after 100 s.

The paper's own figure script avoids this by passing `mixing=0.2` (`make_figures.py:243`), which the listing does not.

The underlying problems are as follows:

- **SCF loop** (`non_interacting.py:313`): `while convergence > tol` has no iteration cap, no detection of stagnation or oscillation, and no warning. The only mixing is fixed linear density/density-matrix mixing.
- **Ground-state reverse engineering** (`reverse_engineering.py:59`): same unbounded `while` loop. The default `tol=1e-12` (line 23) on ∫|n − n_T| dx is far tighter than the 10⁻⁸ actually used for Fig. 2 (`make_figures.py:285`).
- **Time-dependent reverse engineering** (`reverse_engineering.py:207-224`):
  - `scipy.optimize.root(..., method="hybr", options={"maxfev": 200})`. Its forward-difference Jacobian alone needs N_x+1 evaluations, so for N_x ≥ 200 the solver cannot even complete one Jacobian.
  - `result.success` is never checked, and `result.x` is used unconditionally.
  - The residual has a gauge zero mode (a spatially constant δv does not change n), so the Jacobian is singular.
  - The per-step error is returned but nothing acts on it.

Requested changes:

- Fix the listing, and run it in CI (for example as a doctest or smoke test).
- Add `max_iter` and a warning or exception to the SCF and reverse-engineering loops.
- In the time-dependent inversion, check `result.success`, fix the gauge (for example remove the mean, or pin δv at one point), and raise or scale `maxfev`.
- In the paper, report the mixing, tolerances and (μ, p) used for every result.
- Qualify "converges reliably for single systems" (Conclusions). The Hartree example above is a single, simple system for which the default SCF does not converge.

### M3. The LDA is spin-polarised only but is applied to any spin configuration; the hybrid form is non-standard

`lda.exchange_correlation_potential` and `exchange_correlation_energy` always use the `"spin_polerised"` parameters (`lda.py:80-81`, `194-195`), as a function of the *total* density. The same v_xc is added to both spin channels (`lda.py:178`). There is no LSDA and no unpolarised parametrisation.

For `"ud"` systems the method therefore applies a fully polarised electron-gas functional to an unpolarised density. For the singlet atom above, it gives E_LDA = -1.7583 Ha against E_exact = -1.7223 Ha. The hybrid inherits this behaviour.

The manuscript says only that the LDA "uses the exchange and correlation energies of the spin-polarised 1D homogeneous electron gas". It should say explicitly, in Sec. 2 and in the program-summary restrictions, that the functional is spin-polarised only and is applied unchanged to unpolarised and partially polarised systems. Better still, implement or warn for `up_count != count`.

Two further points on this part of Sec. 2:

- **Hybrid form.** It is α v_x^HF + (1−α) v_xc^LDA (`hybrid.py:61-63`). LDA *correlation* is therefore scaled by (1−α), unlike PBE0-type hybrids, and the default α = 0.8 (`hybrid.py:67,93,123`) is not given in the text. Please state the form, the default value, and its origin (for example Ref. [26]).
- **Parametrisation provenance.** Please give which functional form and which table of which reference supplies the exchange fit (a polynomial times n^0.736) and the correlation fit (`lda.py:22-64`). The citation currently covers both Ref. [24] and Ref. [25]; Ref. [24] is the finite-slab LDA paper, whose LDAs are not the HEG LDA.

### M4. KS-SCE is advertised as part of the common framework but is not usable as described, and its total energy is wrong

The abstract and Sec. 2 list KS-SCE among the methods that "share a common interface". In the code:

- **Not part of the common interface.** It is absent from `iterate_methods`, `iterate_sb_methods` and `__all__` (`__init__.py:19-53`).
- **Undocumented attributes.** It requires the user to attach `s.interaction`, `s.dinteraction` and `s.ddinteraction` to the `System` object (`kssce.py:174,177,180`). The tutorial notebook calls this a "quick hack", and `System` does not define these attributes.
- **Crash on the paper's test system.** On the paper's He-like atom (`-2/(|x|+1)`, 101 points on [-10, 10]), `kssce.solve` raises `ValueError: x must be strictly increasing` in `interpolate_invNe`. The cumulant N_e(x) is not strictly monotonic where the density underflows in the tails. It worked for the harmonic-well example in the tutorial.
- **Different signatures.** `kssce.propagate` has a different signature from the other methods (no `hamiltonian_function` argument), and there is no `kssce.propagate_step`, so it cannot be used with `reverse_propagation`.
- **Total-energy bug.**
  - `kssce.py:206` fixes the arbitrary constant in v_SCE with `v_sce + E_sce / s.count * s.dx - np.sum(v_sce * n) / s.count * s.dx`. This enforces ∫v_SCE n dx = E_SCE·δx, not E_SCE as the comment intends.
  - `total_energy` (`kssce.py:288`) then returns Σε + E_SCE.
  - The result is off by E_SCE·δx. For two `uu` electrons in the tutorial harmonic well I obtain errors of 0.047 Ha at δx = 0.20 and 0.023 Ha at δx = 0.10, consistent with E_SCE·δx.

Either fix, document and validate KS-SCE (for example against the strong-interaction limit, or Malet & Gori-Giorgi's published 1D results), or remove it from the abstract and the method list, or label it experimental.

### M5. Exact solver: the spin handling, the eigenpair heuristic and an indexing bug need correcting or disclosing

**(a) The spin string fixes only S_z, not S.** The spin function is a single product state built from the string (`interacting.py:297-304`). The antisymmetriser therefore projects onto the S_z sector, and spatially antisymmetric eigenvectors do *not* vanish for mixed strings. For example, `"ud"` with k = 1 returns the M_S = 0 component of the triplet: I obtain E = -1.344854 Ha for `ud` k = 1 and identically -1.344854 Ha for `uu` k = 0 on the same grid.

The sentence "Spatial states with the wrong exchange symmetry vanish and are discarded, so the kth surviving state is the kth fermionic eigenstate" holds only for fully polarised strings. Please state that the k-th state is the k-th eigenstate in the given S_z sector, and that states of different total spin are interleaved.

**(b) The number of Lanczos eigenpairs is a heuristic with no check.** `_estimate_level` (`interacting.py:246`) is (|N↑ − N↓| + 1)² · N · (k+1). That is 18 eigenpairs for the `uu` ground state and 48 for `uuu`. Nothing verifies that the k-th fermionic state is among them.

- For non-interacting spin-polarised electrons in a harmonic well, the fermionic ground state of N = 4 lies above 126 non-fermionic product states, but the heuristic requests only 100.
- `antisymmetrize` then builds dense arrays of size 2^N · N_x^N × level (`interacting.py:185-192`).

This N!-type overhead and memory footprint, not just "the N_x^N grid", is what limits the method in practice. The approach "without imposing symmetry on the spatial problem" is presented as an advantage; please quantify its cost, add a runtime check (with an error) that at least k+1 antisymmetric states were found, and discuss the alternative of a symmetry-adapted basis.

**(c) Indexing bug for excited states with degenerate spatial multiplets.** After duplicate removal, `spaces` and `spins` are *truncated* to the first M entries rather than filtered with the same mask as `fulls` and `energies` (`interacting.py:228-229`).

For `"uud"` (21-point harmonic well, `level=40`), ⟨space_k|H|space_k⟩ equals E_{k−1} rather than E_k for k = 1, 2, 4, …:

| k | energy | ⟨space_k\|H\|space_k⟩ |
|---|---|---|
| 1 | 1.7636 | 1.6350 |
| 2 | 1.8599 | 1.7636 |

`propagate` starts from `state.space` (`interacting.py:472-474`). Propagating an excited state of such a system therefore propagates the wrong state. Please fix the bug and add a regression test for an N = 3 mixed-spin case.

### M6. Time-propagation accuracy is not demonstrated, and the time-dependent validation is weaker than stated

**Order of the integrator.** Ψ(t+δt) = exp[−iδt Ĥ(t+δt)]Ψ(t) (`interacting.py:417-421`) is first order in δt for a time-dependent Ĥ. The time-dependent mean-field methods build Ĥ explicitly from the density at t (`non_interacting.py:390-396`), with no predictor-corrector or self-consistency within the step. They renormalise each orbital but never re-orthogonalise (`non_interacting.py:410-416`). Please state the formal order and the time step used, and show δt convergence of the dipole in Fig. 3 (for example δt = 0.1, 0.05 and 0.025).

**The time-dependent test does not test time stepping.** The test behind Table 1(b) (`tests/test_time_evolution.py`):

- uses **one** electron;
- starts from the **second excited state** (`"State": 2`) of the displaced well, not the ground state the text implies;
- applies a perturbation that is **constant in time** (`v_ptrb[j,:] = -e*x` for all j).

The exponential is then exact for every step, so the 2×10⁻¹³ agreement tests only `expm_multiply`. It does not test time-stepping error, the interaction, or antisymmetrisation in the dynamics.

Please add a two-electron time-dependent test with a genuinely time-dependent field. The dynamic harmonic-potential theorem is ideal: for interacting electrons in a harmonic well driven by a uniform E(t), the density translates rigidly following the classical centre-of-mass equation. This gives an analytic reference that includes the interaction. Please also correct the text: "a single electron displaced in a harmonic well and released undergoes coherent oscillation ..., which the propagator reproduces at every time step".

### M7. The quantitative tail comparison in Fig. 2 is dominated by the gauge choice and edge artefacts

The figure script makes every potential vanish at the left box edge, `v - v[0]` (`make_figures.py:306-308`). That is exactly where the reverse-engineered potential is least determined: n(−12) = 8×10⁻⁷ for the triplet and 3×10⁻¹¹ for the singlet. The inversion criterion ∫|n − n_T| dx barely constrains the potential there.

Data from `figures/cache/fig2.npz`, compared with the exact asymptote v_xc → −1/(|x|+1) for this spin-polarised two-electron system:

| x | n(x) | v_xc(x) − v_xc(−12), exact RE | expected from the asymptote | v_c (singlet panel) |
|---|---|---|---|---|
| −11 | 7×10⁻⁵ | −0.018 | −0.006 | −0.043 |
| −10 | 4×10⁻⁴ | −0.029 | −0.014 | −0.043 |
| −8 | 3×10⁻³ | **−0.060** | **−0.034** | −0.044 |

- The exact v_xc drops three times faster than the asymptote between the first two grid points.
- The singlet v_c in Fig. 2(b) shows a spurious −0.04 Ha plateau over the whole plotted range. It is set entirely between x = −12 and −11, whereas v_c should vanish asymptotically.
- The quoted comparison "at x = −8 ... the exact v_xc is −0.060 Ha but the LDA gives −0.029 Ha" is therefore mostly an edge artefact. The LDA number (−0.029) is in fact close to the asymptotically expected −0.034.
- The figure itself does not visibly show "the LDA decays too quickly".

The qualitative statement (an exponential LDA tail versus a −1/|x| exact tail) is correct, but the numerical evidence presented does not support it. Please:

- fix the constant physically, for example by matching v_xc to −1/(|x|+1) in a reliable region or by imposing ε_HOMO = −I from the exact N and N−1 energies;
- mask or grey out regions where n is below a stated threshold;
- show convergence with respect to box length (for example L = 24 and 36) and inversion tolerance;
- consider a logarithmic density inset;
- revise the text and the v_c panel accordingly.

A two-electron singlet also gives an analytic validation of the inversion, since v_KS(x) = ε + ½(√n)″/√n. I strongly recommend adding it to Table 1.

### M8. The GPU claims are inconsistent with the repository and imprecise about algorithms

- **Speed-up contradicts the repository's own documentation.** The paper reports that 20 propagation steps on 300 points go from 3.3 s (CPU) to 0.5 s (GPU). But `benchmarking/gpu_td.py` (docstring, lines 14-20) and `benchmarking/_bench.py:29-32` state that CuPy has no `expm_multiply`, that the GPU path uses the scaled Taylor series in `_expm_multiply_gpu` with roughly 2.6× the mat-vecs, and that "at these grid sizes the GPU is expected to lose". The reference table even sets GPU = 2.5 × CPU per step. Either the plotted run used a different code path (`interacting.py:345` takes CuPy's `expm_multiply` if it exists) or the claim is wrong. Please state the CuPy version and the code path used, and reconcile the documentation.
- **Algorithm statements apply only to the CPU path.** "evaluated ... using the algorithm of Al-Mohy and Higham" is true only on the CPU; the GPU fallback is a Taylor series with scaling m = ⌈‖A‖∞⌉ (`interacting.py:348-361`). Likewise the GPU eigensolver is CuPy's thick-restart Lanczos, not ARPACK (`interacting.py:283`).
- **Unexplained outlier.** The ground-state benchmark `gpu_scaling.png` shows a non-monotonic GPU outlier (about 63 s at N_x = 200, slower than the CPU).
- **Timing protocol.** Timings are single runs, with no versions or thread counts given.

Please give a small table with repeated timings, software versions and thread counts. Also state clearly that only the exact solver's Hamiltonian, eigensolver and propagator run on the GPU; antisymmetrisation, observables and all mean-field methods run on the CPU.

### M9. The validation coverage and CI statements are overstated

- **What CI runs.** "These tests run in continuous integration, and further tests check the self-consistent methods and a reverse-engineering round trip." In fact CI runs only `pytest tests/test_manybody.py::TestShort` (`.github/workflows/test_manybody_short.yml:50`). `test_time_evolution.py` and `test_methods.py` are not in CI, and the harmonic-potential-theorem check exists only in `make_figures.py:129-137`, not in the test suite. Please add them to CI or correct the sentence.
- **Approximate methods.** The approximate methods are never compared with an independent reference: `test_methods.py` checks only particle number and finiteness. The reverse-engineering round trip passes at a 10⁻² tolerance in the potential. Reasonable additions:
  - restricted versus unrestricted HF (see M1);
  - the LDA reproducing the HEG energy for a uniform density in a periodic or large box;
  - the analytic two-electron KS potential (see M7);
  - HF/LDA total energies of the atom against an independent implementation, or published values from Refs. [24-26].
- **Abstract.** The abstract says the methods are validated "against analytic results". Only the exact solver is; please rephrase.

### M10. Positioning and citation accuracy

- **Octopus.** The paper says general-purpose packages "target three-dimensional systems with approximate methods [Octopus, PySCF]". Octopus does support exact many-body solutions of 1D/2D model systems (its "model many-body" mode). It was used for exactly this purpose, for example in Ref. [7] (Helbig et al. 2011). Please correct the sentence. A brief comparison with other 1D exact or benchmark resources would also be useful, such as the DMRG-based 1D benchmarks of Refs. [5,6] and existing 1D inversion work.
- **Ref. [4], Javanainen et al. 1988.** It is cited for the softened interaction, but iDEA's default form is 1/(|x−x′|+1), whereas Javanainen et al. introduced the soft-Coulomb 1/√((x−x′)²+1). Please cite the origin of the |x|+1 form and state that it differs from the soft-Coulomb form, or cite Javanainen only for the general idea of softening.
- **Refs. [32,33], Snyder 2012 and Li 2016.** They are cited in the sentence listing iDEA's uses ("It has also generated exact one-body density matrices for machine learning [31,32,33]"). These works did not use iDEA, so citing them there implies they did. Please move them into a separate clause.
- **Ref. [23], Ruggenthaler 2015.** It is cited among "related studies by others" on xc-potential steps. It is a review of the existence and uniqueness of the TD density-potential map, not a study of steps. Please replace or reword; for example, Lein & Kümmel, PRL 94, 143003 (2005) and Fuks et al. are the usual references for dynamical steps and non-adiabatic features.
- **Refs. [34,35], the Faraday Discussions general discussions.** The first-author attribution "Brandenburg, J. G. and others" should be checked against the published records. Citing general-discussion transcripts as evidence that iDEA "informed community discussions" is weak; consider removing them.
- **Origin of the inversion formula.** The update formula, Eq. (2), should be credited to its origin (Ramsden & Godby / Hodgson et al.) and related to the standard schemes it resembles (van Leeuwen–Baerends [13], Wang–Parr). The per-time-step root-finding inversion should be related to the TD inversion literature, for example Nielsen, Ruggenthaler & van Leeuwen, EPL 101, 33001 (2013), and Jensen & Wasserman, PCCP 18, 21079 (2016). Please also state how it differs from the current-density-based TD reverse engineering used in Refs. [18-20] with earlier iDEA versions.

## MINOR issues

1. **Program summary (CPC requirements).**
   - Add the field "Additional comments including restrictions and unusual features" with the actual restrictions: N ≲ 3; memory scaling 2^N N_x^N × (number of eigenpairs); uniform grid with hard walls; spin-polarised LDA only; GPU path only for the exact solver; KS-SCE status.
   - Add a "Supplementary material" line, or state that there is none.
   - Mark the "previous version" fields as not applicable.
   - The "Developer's repository link" (`github.com/JackWetherell/iDEA`) differs from the README badges, homepage and bug tracker (`github.com/iDEA-org/iDEA`); give one canonical repository.
   - The licence is "GPL v3.0" here, "GPL-3.0" in `pyproject.toml`, "GPL-3.0-or-later" in CITATION.cff, and "version 3 ... or later" in LICENSE. Make these consistent.
   - The dependency list omits `jupyterlab`, which `pyproject.toml` makes a hard runtime dependency. Make it optional, or list it.
   - Python ≥ 3.8 is claimed but CI tests only 3.10, and 3.8 is end-of-life.
   - Give the version (1.1.0) and the documentation URL (readthedocs).

2. **Sec. 2, "Systems".** "The default interaction is the softened Coulomb interaction". `v_int` is a required argument of `System` (`system.py:70-76`), so there is no default. Rephrase as "the interaction most commonly used, provided by `interactions.softened_interaction`, is ...". Also, the interaction diagonal is built as `log(einsum(exp(v_int)...))` (`interacting.py:119`), which can overflow for strong interactions; a direct sum is safer.

3. **Defaults.** Please state the defaults:
   - reverse engineering: μ = 1, p = 0.1, tol = 10⁻¹² (`reverse_engineering.py:21-23`);
   - SCF: mixing = 0.5, tol = 10⁻¹⁰;
   - hybrid: α = 0.8.

   Also say that the figures use mixing = 0.2 and tol = 10⁻⁸.

4. **Excited Slater determinants.** "Excited Slater determinants are obtained by occupying higher orbitals." The SCF is converged with ground-state occupations; `add_occupations` then re-occupies after the fact and ranks configurations by the sum of eigenvalues (`non_interacting.py:155-211`, `358`). These are not self-consistent ΔSCF states, and the ranking is not by total energy. Say so.

5. **Common interface.** "Every method module exposes the same functions" should be qualified, because the signatures differ:
   - `interacting.solve(s, H, k, level, GPU)` versus the mean-field `solve(s, k, restricted, mixing, ...)`;
   - `hybrid.hamiltonian` requires an `alpha` kwarg, so `reverse_propagation` with the hybrid method raises `KeyError`: `propagate_step` is called without kwargs (`reverse_engineering.py:227-235`);
   - `hybrid.total_energy` has its own `alpha` default (`hybrid.py:67`), which must match the value used in `solve`;
   - `kssce.propagate` differs (see M4).

6. **Validation text.** "a relative-coordinate problem, which is solved on a fine grid" contradicts "the reference uses the same finite-difference stencil". In the test, du = δx and the same 13-point stencil is used (`test_manybody.py:221-224`). Say "on the same grid spacing". Also give the Table 1(b) system (`uu`, N_x = 151, L = 20) and attribute the 4×10⁻⁸ deviation to discretisation, which breaks exact centre-of-mass separability.

7. **Harmonic-potential theorem wording.** "The lowest dipole excitation of interacting electrons in a harmonic well has energy exactly ω". The theorem guarantees a Kohn mode at ω, not that it is the lowest excitation. Rephrase, and say the check is done for the `uu` case only.

8. **Hardware for the timings.** Table 1(d) and the "about 80 s" for Fig. 3 refer to "the test machine", which is never specified. The Table 1(d) CPU times (21.5 s at N_x = 220) are also inconsistent with the CPU curve in `benchmarking/gpu_scaling.png` (about 7–16 s at 200–250 points). Give CPU model, core and thread count, BLAS, and NumPy/SciPy versions.

9. **Conclusions.** "limited in practice to two or three electrons on grids of a few hundred points (Table 1)". Table 1 shows N = 3 only up to N_x = 40 (19.7 s). For N = 3 at a few hundred points, the dense arrays in `antisymmetrize` alone would be tens of GB. Rephrase, for example "two electrons on a few hundred points or three electrons on a few tens of points".

10. **Fig. 1 discussion.**
    - "HF, which is free of self-interaction for this system": HF is free of one-electron self-interaction in general; drop "for this system".
    - Say what the figure shows for the LDA: a deficit near |x| ≈ 2 and an excess near |x| ≈ 4.
    - The non-interacting density error (0.418, `\numdnnoninteracting`) is computed but not quoted. Note that Hartree (0.654) is worse than non-interacting.
    - The HF and hybrid error curves are invisible at the scale of panel (b); use an inset or a symlog axis.
    - The legend in panel (a) overlaps the curves.

11. **Fig. 3.**
    - The pulse "duration 1 a.u." is in fact 0.9 a.u. Propagation step j uses `v_ptrb[j]`, and `t < 1` selects j = 0..9, so only steps 1–9 (9 × 0.1 a.u.) feel the field (`make_figures.py:364`; `interacting.py:417`).
    - Note that the approximate methods start from different ground states, so the frequency differences mix ground-state and kernel effects.
    - Give the exact oscillation frequency, and mention that t_max = 100 covers about 1.3 periods.

12. **Figure typography.**
    - The legends of Figs. 1 and 3 render a literal "Hartree--Fock"; Matplotlib does not convert `--` to an en dash. Use "Hartree–Fock" (Unicode) or `"Hartree–Fock"`.
    - Tick and legend fonts differ from the serif body text; consider `mathtext.fontset="stix"` for consistency.

13. **Observables.** The kinetic energy of a `ManyBodyState` is not available: `observable()` raises `NotImplementedError` for many-body states (`observables.py:35`). Since T versus T_s (T_c) is a quantity users of exact KS potentials routinely want, either implement it or state the limitation.

14. **Unused material.** The macros `\numvcMin`, `\numtdTmax`, `\numdnnoninteracting`, `\numtimeMaxTwo`, `\numtimeMaxThree`, `\numgridMaxTwo` and `\numgridMaxThree` are generated but unused, and `refs.bib` contains the uncited `Kohn1996`. Harmless, but tidy up or use them; for example, quote the minimum of v_c once it has been corrected per M7.
